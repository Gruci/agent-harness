# agent-harness v1.3 최종 평가

> 담는 것: 통합된 v1.3의 효과와 한계에 대한 판단. 담지 않는 것: 추가 구현 계획의 승인. 읽는 시점: 실제 제품 저장소에 도입하거나 다음 개선의 우선순위를 정할 때.

## 평가 범위와 근거

평가 대상은 개발 저장소 `Gruci/agent-harness-dev`의 통합 커밋 `c5eac17fd72aa53709cf0a68fc0dba8d6c03934e`다.
이 커밋은 로컬 `master`와 `origin/master`에 반영됐다.
공개 저장소 배포는 이번 범위에 포함하지 않았다.

해당 커밋의 [전체 회귀 CI](https://github.com/Gruci/agent-harness-dev/actions/runs/39398248333)는 **543 passed, 7 skipped, 260 subtests passed**로 끝났다.
[기본 검사 CI](https://github.com/Gruci/agent-harness-dev/actions/runs/39398248315)와 [TEAM 승인 CI](https://github.com/Gruci/agent-harness-dev/actions/runs/39398279459)도 통과했다.
SKIP은 검증 성공으로 계산하지 않는다.
이 결과는 하네스 회귀의 근거이며 외부 제품의 생산성 개선이나 실제 다중 PC 운영 안정성을 입증하지 않는다.

## 총평

**종합 6.6/10: 협조하는 코딩 에이전트의 변경 절차를 통제하는 도구로는 실효성이 있다.**
점수는 아래 다섯 축의 단순 평균이며 운영 성숙도 인증이나 측정된 생산성 지표가 아니다.
소규모 팀에서 도입 실험을 할 수준에는 도달했지만 범용 병렬 개발 플랫폼으로 평가하기에는 근거가 부족하다.

가장 강한 부분은 **완료 주장과 실행 근거를 같은 커밋에 연결한 것**이다.
선언한 제품 테스트가 실제로 실행됐는지와 테스트한 작업 트리가 검증한 후보와 같은지를 확인한다.
이전의 구조 검사 중심 완료 판단에서 중요한 진전이다.

가장 큰 아키텍처적 약점은 **Git 작업 사본 격리와 실행 자원 격리 사이의 공백**이다.
파일을 나눠도 DB와 포트와 캐시를 같이 쓰는 병렬 에이전트는 서로의 결과를 오염시킬 수 있다.
README가 이 한계를 명시한 것은 정확하지만 한계를 해결한 것은 아니다.

## 1. 세션 간 컨텍스트 영속성

계획과 거절 이유와 교훈을 Git에 남기는 방식은 대화 기록에 의존하는 것보다 인수인계 근거가 명확하다.
하네스 지도 분할은 세션이 매번 큰 정본 전체를 읽는 비용을 줄인다.
문서 크기를 실패 조건으로 곧바로 승격하지 않은 결정도 기존 프로젝트 도입 마찰을 줄인다.

그러나 크기 알림은 검색 품질이나 기억의 유효성을 보장하지 않는다.
현재 결정과 과거의 보류 결정이 충돌할 때 무엇을 먼저 읽고 무엇을 버릴지 판단하는 구조가 충분하지 않다.
프로젝트가 커지면 개별 문서보다 여러 정본과 관련 교훈을 함께 읽는 누적 비용이 병목이 된다.
16k 추정치 아래로 나눴다는 사실만으로 세션 전체 컨텍스트 예산이 보장되지는 않는다.

근거: [문서 크기 추정과 보고](../../kernel/gates/md_style.py), [수명주기와 교훈 절차](../../dev/harness/lifecycle.md).

## 2. 가드레일과 에이전트 자율성

제품 테스트의 새 JUnit 보고서와 실행 건수를 요구하고 실패 보고서는 명령의 exit 0보다 우선시한 점은 타당하다.
실행 중 HEAD나 작업 트리가 바뀌면 완료로 인정하지 않는 것도 실제 결함을 막는 계약이다.
도구 오류를 실패와 구별한 것은 에이전트가 환경 문제를 제품 수정으로 해결하려는 낭비를 줄인다.

반면 파일 400줄과 함수 80줄 및 중복 탐지는 설계 품질의 대리 지표다.
정상적인 코드 생성이나 긴 선언도 걸릴 수 있으며 실제 오탐률과 재시도 비용은 측정하지 않았다.
JUnit을 만들 수 없는 검사에는 어댑터가 필요하므로 실행기 도입 비용도 생긴다.
무한 수정 루프가 해결됐다고 주장할 근거는 없다.

가장 중요한 조건은 `TESTS`와 `REQUIRED_CHECKS`가 선택 설정이라는 점이다.
설정하지 않은 상태의 finish 성공을 제품 테스트 통과로 해석하면 v1.3의 핵심 이점을 얻지 못한다.
수동 push 훅은 제품 테스트까지 실행하지 않으므로 원격의 필수 CI 설정도 필요하다.

근거: [테스트 실행 계약](../../kernel/tests_run.py), [필수 검사 판정](../../kernel/required.py), [완료 후보 재확인](../../kernel/finish_checks.py).

## 3. 멀티 에이전트와 동시성

남의 worktree를 한 줄 예외보다 먼저 차단한 수정은 소유권 경계를 실제로 강화했다.
경로의 탭과 개행을 처리하고 원격 이동 뒤 따라잡은 후보에서 제품 테스트를 다시 실행하는 회귀도 의미가 있다.
이것은 단순히 보드에 파일 이름을 적는 것보다 강한 보호다.

그러나 touch 대조는 기본적으로 경고이며 선언한 범위가 실행 자원 전체를 표현하지는 않는다.
서로 다른 파일의 API와 소비자 수정은 파일 충돌 없이도 통합 시 실패할 수 있다.
DB 마이그레이션과 공유 캐시 및 포트 경합도 worktree로 해결되지 않는다.
선택형 TEAM의 예약과 승인 경로가 통과했다는 사실을 실제 여러 PC의 장기간 운영 검증으로 확대하면 안 된다.

근거: [소유권 검사](../../kernel/isolation.py), [touch와 후보 검사](../../kernel/finish_checks.py), [재시도 통합 절차](../../kernel/task_finish.py).

## 4. 도입 마찰과 개발자 경험

템플릿은 전체 절차를 도입하고 플러그인은 검사를 먼저 도입하는 구분이라 선택 자체는 합리적이다.
두 방식의 보장 범위를 README에서 분리하고 SKIP과 보안 경계를 설명한 것은 기대 수준을 바로잡는다.
작은 수정의 계획 생략과 조기 경고도 불필요한 승인 횟수를 줄인다.

다만 프로파일과 컴포넌트 분류 및 훅 신뢰와 CI를 모두 맞춰야 효과가 난다.
기존 저장소에서는 기존 위반 정리와 업그레이드 충돌 검토가 별도 비용이다.
범위 질문과 계획 승인이 반복되는 흐름은 요구가 자주 바뀌는 탐색 작업에서 느릴 수 있다.
실제 승인 대기 시간과 신규 사용자 완료 시간을 측정하지 않았으므로 README 개선만으로 DX 점수를 크게 올리기는 어렵다.

근거: [설치와 보장 범위](../../README.ko.md), [변경 절차](../../dev/workflows/feature-workflow.md).

## 5. 자가 개선 메커니즘

반복 관측 횟수와 물리 배치 ID를 나눠 복구와 재flush의 중복 합산을 막은 것은 기록의 신뢰도를 높였다.
교훈에 강제 수단을 연결하고 회고 판정에 근거를 남기는 구조도 규칙의 이유를 추적하는 데 유용하다.
재현한 기록 손실과 중복 문제를 회귀로 남긴 점은 이번 개선의 실질적 성과다.

그러나 반복 횟수는 실패한 수정 시도 수나 회복 시간과 같지 않다.
Lesson을 새 검사로 설계하고 검사의 오탐을 판단하고 오래된 규칙을 폐기하는 일은 여전히 사람이 한다.
근거 문자열과 검사 연결만으로 충돌하는 규칙의 우선순위가 자동 결정되지는 않는다.
현재는 자동 자가 진화보다 사람의 유지보수를 돕는 관측과 기록 체계에 가깝다.

근거: [관측 합산과 복구](../../kernel/trace.py), [회고 판정](../../kernel/retro.py), [교훈의 강제 수단 검사](../../kernel/gates/harness_self.py).

## 경쟁 패러다임에서의 위치

| 접근 | 이 하네스와의 차이 | 선택 기준 |
|---|---|---|
| 단일 지침 파일 | 읽기 규칙만 두는 방식보다 기계 검사와 과업 종료 절차가 강하다 | 짧은 개인 작업에서는 설정과 운영 비용이 더 클 수 있다 |
| 저장소 기반 하네스 | Git 기록과 개발자 도구를 중심으로 변경을 통제한다 | 여러 세션이 같은 제품을 이어서 고칠 때 적합하다 |
| 실행 루프를 소유하는 에이전트 프레임워크 | 실행기 전체를 소유하는 설계와는 제어 경계가 다르다 | 자원 격리와 재현 가능한 실행 환경이 필요하면 별도 계층이 필요하다 |

이 비교는 설계 방식의 차이다.
특정 경쟁 제품의 최신 기능이나 성능 우위를 측정한 비교는 아니다.

## 다음 개선 과제 세 가지

| 우선순위 | 구체적인 작업 | 필요한 이유와 완료 기준 |
|---|---|---|
| 1 | 실제 도입 제품에서 `TESTS`와 필요한 `REQUIRED_CHECKS`를 설정하고 원격 필수 CI를 연결한다 | 테스트 0건과 도구 누락 및 후보 변경이 실제 병합을 막는지 확인해야 선택 기능이 운영 계약이 된다 |
| 2 | 병렬 통합 테스트를 쓰는 제품에서 작업별 DB 또는 스키마와 포트 및 캐시를 나누고 마이그레이션 통합을 직렬화한다 | 실제 자원 충돌 재현을 통과해야 worktree 밖의 공백을 메운 것으로 본다 |
| 3 | 오탐이 문제 되는 검사에 정상 사례와 사고 사례를 함께 두고 회고 근거를 회귀와 연결한다 | 차단 재시도와 승인 대기 시간을 작은 도입 실험에서 측정한 뒤 규칙 승격과 폐기를 판단한다 |

측정 없이 새 전역 임계값이나 자동 규칙 폐기부터 추가하면 유지보수 대상만 늘어난다.
다음 버전은 검사 수 증가보다 실제 제품 한 곳에서의 오탐과 충돌 및 완료 시간 검증을 우선해야 한다.
