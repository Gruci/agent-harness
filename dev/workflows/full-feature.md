# 풀스택 구현 절차

> 담는 것: 서버와 화면의 공동 구현 및 경계 검증. 담지 않는 것: 연구와 승인 절차(→ `feature-workflow.md`). 읽는 시점: 서버와 소비 화면을 함께 변경할 때.

## 시작

[feature-workflow.md](feature-workflow.md)의 리서치와 계획 승인을 먼저 완료한다.
기존 결과를 보완하는 요청이면 해당 부분만 다시 수행한다.
다른 미완료 작업 문서를 덮어쓰지 않는다.

## 인터페이스 확정

| 항목 | 양쪽이 공유할 내용 |
|---|---|
| 요청 | API 경로와 메서드 및 파라미터명 |
| 응답 | 키 이름, 타입, 중첩 구조, null과 빈 결과 |
| 화면 | 데스크톱과 모바일 배치 및 전환 방식 |
| 파일 소유권 | 서버와 프론트엔드의 겹치지 않는 편집 범위 |

인터페이스를 계획에 기록한 뒤 구현한다.
파일이 겹치면 순차로 수행한다.

## 구현 배정

- 독립적인 서버와 화면 작업은 선택적으로 병렬 위임할 수 있다.
- 각 워커에게 목표와 소유 파일 및 확정된 인터페이스를 전달한다.
- 화면 워커에게 반응형 설계표도 전달한다.
- 양쪽 모두 해당 정본 문서와 검사 규칙을 따른다.
- 위임이 불가능하면 메인 세션이 같은 범위를 직접 수행한다.

## 통합 검증

- API가 반환하는 필드를 프론트엔드가 실제 읽는 필드와 하나씩 대조한다.
- null과 빈 결과에서도 화면의 정상 동작을 확인한다.
- 새 API의 소비 컴포넌트가 실제 화면에서 사용되는지 확인한다.
- 관련 테스트와 타입 검사 및 렌더링 검사를 실행한다.
- 불일치를 담당 구현에서 수정한 후 경계를 다시 검증한다.
- 독립 검토자를 사용할 수 있지만 메인 세션이 결과와 완료 여부를 확인한다.

## 실패와 완료

| 상황 | 다음 행동 |
|---|---|
| 워커 실패 | 실패 근거를 지시에 보태 한 번 재시도하거나, 메인 세션이 넘겨받아 직접 한다 |
| 재시도 실패 | 원인을 해결해 필수 작업을 끝내거나, 막힌 이유를 근거와 함께 보고 |
| 파일 소유권 충돌 | 병렬 편집을 중단하고 순차 통합 |
| 세 번 고쳐도 불일치 | 인터페이스 설계를 재검토하고 판단이 필요한 부분을 사용자에게 제시 |

실패한 서버나 화면 작업을 제외하고 기능이 완료됐다고 보고하지 않는다.
필수 범위 변경에는 사용자의 결정이 필요하다.
최종 정리는 [feature-workflow.md](feature-workflow.md)의 완료 절차를 따른다.
