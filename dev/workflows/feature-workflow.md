# 기능 변경 절차

> 담는 것: 범위 확인부터 구현 검증과 정리까지의 공통 절차. 담지 않는 것: 작업 격리 운영(→ `../../workboard/README.md`). 읽는 시점: 오탈자나 설정값 하나를 제외한 코드 변경 요청 시.

## 범위와 기존 작업

- 메인 세션이 리서치와 계획을 직접 수행한다.
- 기존 작업 문서를 확인하고 후속 요청이면 해당 단계만 재실행한다.
- 다른 작업의 끝나지 않은 문서를 덮어쓰거나, 끝난 것처럼 archive로 옮기지 않는다.
- 작업 문서는 `docs/tasks/research_<task>.md`와 `docs/tasks/plan_<task>.md`를 쓴다.
- 범위, 화면 노출, 데이터 적재 가운데 아직 정해지지 않은 중요한 사항만 먼저 묻는다.
- 요청과 기존 문서에 결정이 있으면 인터뷰를 반복하지 않는다.

요청에 아래 세 가지 결정이 모두 담겨 있으면 인터뷰 없이 바로 리서치한다.

| 항목 | 필요한 결정 |
|---|---|
| 범위 | 만들 기능과 범위 밖 항목 |
| 노출 | 화면과 위치, 또는 화면 없음 |
| 데이터 | 원천과 적재 및 갱신 방식 |

## 리서치

- 관련 구현과 동작하는 유사 사례를 읽는다.
- 내부 로직과 데이터 흐름을 따라 호출자와 소비처까지 확인한다.
- 버그는 재현하고 원인을 추적한다.
- 조사 근거와 현재 동작을 연구 문서에 기록한다.
- 이 단계에서는 소스를 수정하지 않는다.

## 계획과 승인

연구 결과를 바탕으로 구현 가능한 계획을 작성한다.

| 계획 항목 | 완료 기준 |
|---|---|
| 접근 방식 | 실제 코드 문맥의 핵심 변경 예시와 정확한 대상 경로 |
| 업무 행동 | 사용자가 얻는 결과와 보존할 업무 규칙 |
| 정책과 경계 | 정책과 유스케이스 및 필요한 포트의 책임 |
| 분류 제안 | 새 이름과 책임 및 제외 범위를 사용자에게 제안한다 |
| 그래프 변경 | 기존 정본과 제안의 차이 및 실제 사용자 응답 기록 |
| 결정 지연표 | 지금 필요한 기술과 일부러 뒤로 미룰 결정 |
| 파일 설계표 | 경로마다 맡을 책임 하나와 예상 규모. 길이 상한에 가까우면 미리 나눈다 |
| 반응형 설계표 | 화면별 데스크톱과 모바일 배치 및 전환 방식 |
| 행동 테스트 | 정책과 경계별 실패를 검출할 시나리오와 테스트 경로 |
| 병렬 후보 | 워커끼리 겹치지 않게 나눈 편집 파일. 위임하지 않으면 그 이유 |
| 아키텍처 변경 | 의존 방향이 바뀌면 `../DIAGRAM.md` 절차로 만든 컴포넌트 지도의 변경 전후 비교 |
| 호환성 | 깨지는 계약과 선택의 비용 |
| 배포 영향 | 배포 단위와 순서 및 실패 복구 |
| 인수인계 | 다음 세션이 확인할 계약과 남은 결정 |

화면 설계 기준은 `../../design/RESPONSIVE.md`를 따른다.
미정 참조나 자리표시자가 남은 계획을 구현에 넘기지 않는다.
계획을 사용자에게 보여주고 명시적으로 승인받은 뒤 구현한다.
기존 대화에서 구체적인 제안과 범위를 이미 승인했다면 그 근거를 계획에 기록하고 진행한다.
같은 범위의 승인을 다시 요구하지 않는다.
분류 승인 기록은 [컴포넌트 절차](../COMPONENTS.md)를 따른다.
사용자가 답하지 않은 제안을 승인으로 기록하지 않는다.
로컬 기록의 일관성 검증을 사용자 신원 인증이라고 설명하지 않는다.
사용자가 계획을 수정하면 메모의 의도와 제약을 반영한다.
승인 범위가 실질적으로 달라지는 선택이면 바뀐 계획을 다시 보여 준다.

## 구현과 위임

- 구현을 시작할 때 `../../workboard/`의 열린 과업을 확인하고, 메인 세션이 자기 세션 ID를 붙인 과업 파일을 등록한다. 같은 범위의 과업이 이미 있으면 그 과업에 항목을 더하거나(합류) 그 과업 브랜치 위에서 작업한다(쌓기). 정본은 그 디렉토리의 README다.
- 구현은 자기 worktree에서 한다. 메인 체크아웃에서 편집하거나 workboard에 과업을 등록하지 않고 편집하면 편집 전 훅이 막는다(예외: `workboard/`·`docs/tasks/`·바뀐 줄 1줄 이하).
- worktree 안에서는 파일 저장 시점과 턴 종료 시점의 게이트가 막지 않고 `[WIP]` 목록으로 알리기만 한다. 합치기 전에 그 목록을 비운다.
- 새 파일이나 함수를 만들기 전 `../CONVENTIONS.md`와 관련 정본 예시를 읽는다.
- 승인된 계획의 필수 작업을 모두 구현한다.
- 첫 제품 코드는 승인된 그래프의 컴포넌트와 역할에 배치한다.
- 승인된 그래프에 분류되지 않은 변경이 나오면 그 범위의 분류 제안을 사용자에게 알리고, 그와 무관한 작업은 계속한다.
- 메인 세션은 독립적으로 진행 가능한 구현만 선택적으로 위임한다.
- 위임 전 목표, 범위 밖 항목, 계획 경로, 편집 소유권을 확정한다.
- 병렬 위임 직전에 메인 세션이 베이스라인 커밋을 만든다. 전부 되돌릴 때 기준점이 된다.
- 워커는 자기 파일만 편집하고 계획과 작업 보드는 메인 세션이 관리한다.
- 겹치는 파일의 변경은 순차로 통합한다.
- 워커가 끝나면 메인 세션이 실제 변경 경로를 배정 범위와 대조한다.
- 메인 세션이 통합과 최종 검증을 책임진다.
- 위임 기능이 없어도 같은 범위를 직접 완료한다.

## 검증과 수정

- [test.md](test.md)에 따라 변경 계약을 검증하고 실제 명령의 종료 코드를 기록한다.
- 버그 수정은 재현 테스트 통과를 확인한다.
- 화면 작업은 렌더링 결과도 확인한다.
- 실패 원인을 확인해 가장 작은 가설 하나씩 검증한다.
- 수정 시도가 세 번 실패하면 편집을 멈추고 근거와 설계 문제를 보고한다.
- 부분 수정은 요청한 범위로 제한한다.
- 롤백은 명시적으로 요청된 자기 변경만 대상으로 하며 관련 없는 편집을 보존한다.

## 완료

1. [code-trim.md](code-trim.md)로 현재 diff를 검토한다.
2. 승인 범위 안의 단순화가 필요하면 구현 작업으로 반영하고 검증한다.
3. 오래 유지되는 계약이 바뀌었으면 그 정본 문서를 같은 턴에 갱신한다.
4. `python -X utf8 -m kernel.runner --verify`와 변경에 맞는 검사를 통과한다. push·PR·merge 직전에는 훅이 같은 `--verify`를 그 체크아웃에서 다시 돌리고, exit 0이 아니면 막는다.
5. 메인 세션이 계획의 완료 상태와 검증 근거를 정리한다.
6. 두 작업 문서를 `docs/tasks/archive/YYYY-MM-DD-<task>/`로 같은 턴에 보관한다.
7. worktree 같은 작업 격리 환경을 필요한 만큼 정리한 뒤 자기 과업 파일만 지운다.

실패한 필수 작업을 빼고 완료라고 보고하지 않는다.
커밋과 외부 반영은 실행 환경의 지침과 사용자 승인 범위를 따른다.
