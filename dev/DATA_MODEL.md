# dev/DATA_MODEL.md — DB 설계도

> 담는 것: 테이블 정의의 정본, 차원과 팩트를 가르는 설계 원칙, 신규 테이블 표준 절차. 담지 않는 것: 컬럼 이름 규칙(→ `dev/NAMING.md`)·컴포넌트 경계(→ `dev/ARCHITECTURE.md`). 읽는 시점: **DB 테이블이나 컬럼을 추가·수정하기 전, 예외 없이.**

아직 스키마가 없다. 첫 테이블 설계 시 아래 절차를 따르고 이 문서에 등재한다. 왜 이 문서가 강제인지는 `dev/LESSONS.md` §9에 있다.

## DB 설계 표준 절차 (테이블/컬럼 추가 전)

1. **이 문서의 테이블 목록을 먼저 확인** — 같은 데이터가 이미 어느 차원이나 테이블에 있는지 본다. 중복 컬럼을 새로 만들지 않는다.
2. **차원 vs 팩트 구분** — 불변 속성(이름·분류·카테고리)은 차원 테이블 한 곳에만. 측정값(일별 수치)만 팩트 테이블에. 차원 컬럼을 팩트 테이블마다 복제(denormalize)하지 말고 JOIN한다.
3. **확장성 점검** — "카테고리/국가/자산군이 하나 더 들어오면?" 차원 테이블에 row 를 추가하는 것만으로 끝나야 정상이다. 팩트 테이블마다 컬럼을 추가해야 하는 설계라면 틀렸다.
4. **컬럼 네이밍** — `dev/NAMING.md`를 따른다. 의미가 드러나는 전체 이름을 쓰고 축약어와 내부 코드는 쓰지 않는다. dict 키, API 필드와 같은 규칙이다.
5. **DDL 위치** — 승인된 어댑터 컴포넌트의 스키마 모듈(`CHECK_PATHS["schema"]`가 가리키는 곳)에 두고, 여러 번 실행해도 결과가 같게(멱등) 만든다. 설계가 확정되면 이 문서에 테이블, 컬럼, 차원/팩트 구분을 등재한다.

## 테이블 목록

| 테이블 | 유형 | 키 | 용도 |
|--------|------|-----|------|

## 공통 규칙

- 날짜 컬럼: `YYYY-MM-DD` 문자열 통일 (`dev/NAMING.md`)
- timestamp: 시간대 없는(naive) 값 금지. 프로젝트가 정한 업무 시간대가 붙은(aware) 값을 쓴다 (`dev/CONVENTIONS.md` 「공통 설계」 시각)
- 0은 유효값이다. NULL로 바꾸지 않는다 (같은 「공통 설계」 표의 숫자 정제 행)
