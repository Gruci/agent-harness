# dev/OVERVIEW.md — 하네스 한눈에: 구조와 용어

> 담는 것: 하네스를 이루는 부품과 변경 한 번이 그 부품을 지나는 길, 문서·출력에 나오는 용어의 뜻. 담지 않는 것: 훅·검사 하나하나의 조건과 근거(→ [하네스 지도](HARNESS.md))·세션 행동 규칙(→ [CLAUDE.md](../CLAUDE.md)). 읽는 시점: 이 하네스를 처음 볼 때, 문서에서 모르는 말이 나왔을 때.

## 하네스가 하는 일

AI 세션이 바뀌어도 한 사람이 작업한 것처럼 이어지게 한다.

- 규칙과 결정을 레포의 문서에 남겨 다음 세션이 읽게 한다.
- 지킬 수 있는 규칙은 문서가 아니라 검사로 만들어 매번 자동으로 돌린다.
- 검사를 통과하지 못한 작업은 본체에 합쳐지지 않는다.

## 부품

| 부품 | 하는 일 | 정본 |
|---|---|---|
| 규칙 문서 | 세션이 지킬 행동 규칙과 무엇을 언제 읽을지 | [CLAUDE.md](../CLAUDE.md) (Codex 는 `AGENTS.md`) |
| 훅 | Claude Code·Codex 가 정해진 순간에 부르는 스크립트. 시작 때 알림을 넣고, 실행 전에 위험한 명령을 막고, 저장·턴 종료 때 검사를 돌린다 | [하네스 지도](HARNESS.md) 「Claude 훅 실행 순서」 |
| 검사(게이트) | 코드·문서 상태를 판정하는 규칙 하나. 파일 길이, 중복, 의존 방향, 색 하드코딩 같은 것 | [하네스 지도](HARNESS.md) 「게이트」 |
| 과업 명령 | 과업을 보드에 올리고(`plan`·`start`), 끝내고(`finish`), 넘겨받고(`resume`), 버리는(`abandon`) 명령. `python -X utf8 -m kernel.task <명령>` | [작업 보드](../workboard/README.md) |
| 스킬·에이전트 | 정해진 절차(설치 인터뷰·기능 작업·감사)를 담은 스킬과, 큰 일을 나눠 맡는 에이전트 정의 | `.claude/skills/`, `.claude/agents/` |
| 러너 | 검사 전체를 한 번에 돌리고 결과를 표시하는 명령. 완료의 근거는 `python -X utf8 -m kernel.runner --verify` exit 0 뿐이다 | `kernel/runner.py` |
| 커널 | 훅·검사·러너를 담은 Python 코드 묶음. 어느 프로젝트에서나 같다 | `kernel/` |
| 프로파일 | 이 프로젝트를 커널에 알려 주는 설정 하나. 언어, 폴더 위치, 예외 목록 | `harness_profile.py`, 서식은 `profiles/_template.py` |
| 팩 | 언어·프레임워크·구조마다 다른 점을 적은 선언 파일. 커널은 그대로 두고 팩만 바꿔 다른 언어로 옮긴다 | [조립 절차](workflows/harness-assembly.md) 「스택 맞춤」 |
| 컴포넌트 그래프 | 제품 코드를 어떤 덩어리로 나누고 어느 쪽이 어느 쪽을 써도 되는지 적은 정본 | [컴포넌트 계약](COMPONENTS.md) |
| 작업 보드·작업 사본 | 누가 무엇을 하고 있는지(보드)와 과업마다 따로 만든 작업 폴더(작업 사본) | [작업 보드](../workboard/README.md) |
| 조사·계획 문서 | 코드 전에 쓰는 research·plan 파일. 끝나면 보관된다 | [기능 변경 절차](workflows/feature-workflow.md) |
| 교훈·거절 기록 | 사고 경위와 그 사고를 막는 검사, 검토하고 채택하지 않은 제안 | [LESSONS.md](LESSONS.md), [REJECTED.md](REJECTED.md) |

## 변경 한 번이 지나는 길

| 단계 | 사람 | AI 와 하네스 |
|---|---|---|
| 1 범위 | 무엇을 바꿀지 답한다 | 범위·노출·데이터가 정해지지 않았으면 묻는다 |
| 2 조사·계획 | 계획 요약 4줄을 보고 승인한다 | research·plan 을 쓰고 작업 보드에 「계획」으로 올린다 |
| 3 구현 | — | 작업 사본을 만들고 그 안에서 고친다. 저장할 때마다 검사가 돌아 위반을 알린다 |
| 4 합치기 | — | `kernel.task finish` 가 전체 검사를 다시 돌리고, 통과하면 본체에 합치고 push 한 뒤 작업 사본을 지운다 |

기존 파일만 고치는 작은 수정은 1·2 단계를 건너뛴다(소규모 경로). 크기는 4 단계에서 실제로 잰다.

## 검사 결과 표시

| 표시 | 뜻 |
|---|---|
| `[OK]` | 검사했고 문제가 없다 |
| `[FAIL]` | 규칙 위반. 고치기 전에는 합쳐지지 않는다 |
| `[WIP]` | 작업 사본 안의 위반. 작업 중에는 막지 않고 합칠 때 막는다 |
| `[SKIP]` | 설정이 비어 검사하지 못했다. 합치기를 막지는 않지만 그 규칙은 아무것도 지키지 않고 있다 — 통과가 아니다 |
| `[N/A]` | 이 언어·구조에서는 성립하지 않는 규칙이다 |
| `[TOOL]` | 필요한 도구나 분석기가 없어 검사하지 못했다. 통과가 아니고 `--verify` 가 exit 2 로 합치기를 막는다 |
| `[DECISION]` | 새 분류가 필요해 사용자 결정을 기다린다. `--verify` exit 3 |
| `[REPORT]` | 확실하지 않은 신호. 막지 않는다 |
| `[RATCHET]` | 과업이 동결 목록에 줄을 더했다는 알림. `finish` 가 내고 막지는 않는다 |
| `[VERIFIED]`·`[UNVERIFIED]` | 팩 적합성 판정(`kernel.pack_check`). 미검증이 하나라도 있으면 1급 팩이 아니다 |

세션 시작 알림도 대괄호 머리를 단다 — `[SESSION]`(이 세션의 sid), `[HARNESS SETUP]`(설정이 덜 끝남), `[MAINTENANCE]`(정비할 때가 됨), `[GITHUB CHECK]`(원격 없음), `[HARNESS]`(플러그인 설치의 연결 상태).
