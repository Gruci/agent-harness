# dev/LESSONS.md — 사고 연대기 (규칙의 배경)

> 담는 것: 규칙이 생긴 실제 사고 경위와 재작업 대가, 그리고 그 사고를 지금 무엇이 막고 있는지. 담지 않는 것: 규칙 자체(→ `CLAUDE.md` 증거·경계 원칙)·코드 관례(→ `dev/CONVENTIONS.md`). 읽는 시점: 규칙이 과해 보일 때, 그리고 새 사고를 겪어 규칙을 늘릴 때.

`CLAUDE.md`는 매 세션 강제 로드되는 RAM이라 **규칙 요지만** 싣는다. 그 규칙이 왜 생겼는지는 전부 여기에 있다.

**이 파일이 하네스를 키운다.** 사고가 나면 여기 경위를 남기고, 기계로 검사할 수 있으면 `kernel/gates/`에 판정을 더한다(이 레포에서만 참인 규칙은 `harness_gates/`). 그때부터 그 규칙은 부탁이 아니라 차단이다. 올릴 수 없으면 왜 못 올리는지를 적는다. 지금 게이트는 전부 이 경로로 생겼다 — 설계된 게 아니라 사고마다 하나씩 늘었다.

각 절은 제목 다음 줄에 강제 수단을 선언한다. 선언 누락과 유령 게이트 번호는 검사 30이 잡는다.

```
> 강제: 검사 1·7             기계가 막는다
> 강제: 산문 전용 — <사유>    기계로 못 잡는다. 사유를 반드시 적는다
```

**산문 전용이 많은 것은 정상이자 경고다.** 그 목록이 곧 "아직 사람 규율에만 기대고 있는 구간"이고, 게이트로 올릴 후보 목록이다.

**출처 표기 원칙** — 아래 §1~§12의 경위는 대부분 **원본 프로젝트(fund_monitor) 실증**이다. 이 하네스가 거기서 이식됐기 때문이다. 이 프로젝트 자체 사고가 생기면 해당 절에 덧붙이고 출처를 구분해 적는다. 남의 사고를 이 프로젝트 이력으로 위장하지 않는다.

**삭제 금지** — 여기 서사는 압축·요약 대상이 아니다. 사고 기록이 사라지면 규칙은 근거 없는 잔소리가 되고, 다음 세션이 같은 사고를 반복한다.

## §0 — 절차 생략의 대가

> 강제: 산문 전용 — 절차 준수 여부는 기계가 검출할 수 없다. 스킬과 훅이 유도할 뿐이다

> 규칙 정본: `CLAUDE.md` 4단계 기능 개발 워크플로우
> 출처: 원본 프로젝트 실증 (2026-05-21)

성능 최적화를 research와 plan 없이 바로 구현했다. Cache-Control 미들웨어와 DB 인덱스와 JS 중복호출 제거를 한 번에 밀어붙였다.
결과: 인덱스 설계가 실제 쿼리 패턴과 맞지 않아 통째로 재작업.

**"간단해 보인다"는 판단은 절차 생략의 근거가 되지 않는다. 예외는 오탈자와 1줄 설정값뿐.**

## §1 — 컨텍스트 압축 후 스테일 Read로 편집

> 강제: 산문 전용 — 컨텍스트 압축 경고는 세션 런타임 신호라 정적 검사 대상이 아니다

대화가 길어지면 이전 Read 결과가 요약된다. system-reminder에 **"was read before the last conversation was summarized"**가 뜨면 그 Read는 **무효**다.

- 편집 대상에 stale 경고가 있으면 편집 전 반드시 재Read.
- **"방금 읽은 것 같다"는 느낌은 근거가 아니다.** system-reminder 텍스트가 기준이다.
- 압축 후에는 함수 시그니처와 줄 번호가 바뀌어 있을 수 있다. 추측으로 Edit하면 엉뚱한 줄을 건드린다.

## §2 — "아마 이럴 것이다" 추론으로 주장

> 강제: 산문 전용 — 근거 없는 단언인지는 의미 판정이다

확인 없이 추론해서 단언하는 패턴이다.

- "이 테이블에 데이터가 있을 것이다" → **쿼리로 확인 후** 말한다.
- "이 함수는 X를 반환할 것이다" → **Read 후** 말한다.
- "아마 이 파일일 것이다" → **Glob·Grep 후** 말한다.
- 확인하지 않았으면 "확인이 필요하다"고 명시한다. 추측을 사실처럼 포장하지 않는다.

실사고는 §9와 겹친다. "전종목 합산이라 시장구분이 없다"고 단언했는데 실제로는 차원 테이블에 멀쩡히 있었다.

## §3 — 변경 영향 범위 3-레이어 미추적

> 강제: 검사 32 — 미정의 상수를 검사한다. 경계는 component_dependencies가 검사한다. 응답 의미의 소비처 추적은 기계가 못 잡는다 — 실제 업무 의미를 이해하는 검토가 필요하다

당시 프로젝트는 도메인 패키지와 DB 및 API와 화면을 고정 경로로 나누었다.
현재 의존 방향은 [컴포넌트 계약](COMPONENTS.md)의 승인된 그래프로 검사한다.

당시 영향 추적에서 놓쳤던 대상:

- `db/reads/` 시그니처나 반환값 변경 → `web/routes/` 호출자 Grep
- `web/routes/` 응답 구조 변경 → `frontend/src/` 소비 훅과 컴포넌트 Grep
- React 컴포넌트·훅·상수 시그니처 변경 → import하는 다른 `.tsx`와 `.ts` Grep
- 배치에서 DB 테이블 구조 변경 → 같은 테이블 읽는 쿼리 전체 Grep

**확인하지 않고 "영향 없을 것이다"라고 판단하는 것은 금지.**

## §4 — "간단해 보인다"로 research·plan 생략

> 강제: 산문 전용 — §0과 같다. 절차 준수는 검출 불가

§0의 반복 위반이다. 추가 기준을 박는다. 아래 중 하나라도 걸리면 research → plan이 필수다.

- 수정 파일이 2개 이상
- 1개 파일이라도 다른 레이어를 호출하거나 다른 레이어에서 호출됨
- "이미 아는 코드다" — 세션 간 변경 가능성이 있어 근거가 안 된다
- 버그 원인이 한 파일에 국한되지 않을 가능성

## §5 — MD 업데이트를 "나중에"로 미룸

> 강제: 검사 25·28·48 — 문서 구조와 하네스 지도와 그림을 검사한다. 경로·함수 참조(26·33)는 `STAGE` 가 greenfield 면 리포트와 SKIP 이고 그 뒤 단계에서 FAIL 로 오른다

연쇄 요청이 이어지면 "지금 급한 것 먼저, MD는 나중에" 패턴이 나온다. **나중은 오지 않는다.**

컨텍스트가 압축되면 무엇을 업데이트해야 하는지도 함께 사라진다. 코드 변경이 끝난 **그 턴** 안에 관련 MD까지 끝낸다.

## §6 — 구현 완료 후 plan·research 방치

> 강제: 산문 전용 — 산출물 방치는 검출 가능하나 작업 중 상태와 구분이 안 된다

`docs/tasks/` 루트에 남은 산출물은 다음 세션에서 **"진행 중인 작업"으로 오해된다.**

모든 Todo 체크 직후 그 턴 안에 `git mv`로 `docs/tasks/archive/YYYY-MM-DD-{작업명}/`으로 옮기고 구현 커밋에 포함한다.

## §7 — 규칙을 작성 시점에 안 지켜 사후 리팩토링 유발

> 강제: 검사 1·2·4·5·7·8 — 파일 크기와 중첩 함수 및 이름과 타입을 검사한다. 업무 분류는 component_classification과 component_dependencies로 검사한다

> 출처: 원본 프로젝트 실증 (2026-06-01)

코드베이스 전수 점검에서 **규칙 위반 208건**이 나왔다. 타입힌트 149건에 축약어와 400줄 초과와 클로저와 읽기쓰기 혼재가 뒤따랐다. **6단계 대규모 리팩토링 사태**로 번졌다.
규칙 MD는 멀쩡히 있었는데 **코드 작성 시점에 적용되지 않아** 누적된 것이다.

사용자: **"처음부터 규칙 맞춰 짰으면 리팩토링 안 했다. 그럴거면 MD 왜 짰냐."**

이 사고가 작성 시점 훅과 Stop 훅으로 이어지는 모든 자동 게이트의 직접적 원인이다.

작성 시점 셀프체크:

- **기존 파일 이어 붙이기 금지** — 코드를 추가하기 전에 "이 코드의 책임이 이 파일의 단일 책임과 같은가"를 자문한다. 다르면 처음부터 별도 파일을 신설한다. 400줄 게이트는 이 습관의 마지막 방어선이지 분리 기준이 아니다.
- 400줄을 넘으면 그 자리에서 기능 단위 분리. "나중에 분할" 금지.
- 업무 책임에 맞는 승인된 컴포넌트에 배치한다. 정본은 [아키텍처](ARCHITECTURE.md)다.
- 정책과 외부 I/O를 분리한다. 고정 함수 접두어나 세 함수 분할을 요구하지 않는다.
- 중첩 def 금지. 모듈 함수와 파라미터 전달로 푼다.
- 축약어 금지. 정본은 `dev/NAMING.md`.
- 함수 시그니처에 타입힌트를 단다.

## §8 — 백엔드만 만들고 소비 UI를 안 만듦

> 강제: 검사 31 — 소비 화면이 없는 라우트를 잡는다

> 출처: 원본 프로젝트 실증 (2026-06-10)

관리자 기능을 레거시 템플릿과 바닐라 JS로 구현했다. 화면은 React SPA가 서빙하므로 **사용자에겐 기능이 통째로 안 보였다.** 뒤늦게 React 포팅으로 복구했다.

사용자: **"내가 코딩할 때 React로 코딩하도록 MD 다 바꿔놓으라고 했지."**

교훈의 핵심은 "레거시를 쓰지 말라"가 아니다. **백엔드만 만들고 소비 UI를 안 만들면 그 기능은 존재하지 않는 것과 같다.** API 라우트를 추가하는 작업은 소비 React 컴포넌트를 같은 작업 안에서 만들어야 완료다.

## §9 — DB 설계 시 확장성과 차원 무시

> 강제: 산문 전용 — 차원 설계의 적절성은 의미 판정이다

> 출처: 원본 프로젝트 실증 (2026-06-24)

DB에는 시간이 지나며 다른 나라와 자산군이 계속 물린다.

사용자: **"db에 데이터 추가될 때마다 설계도 읽고 확장성 고려해서 db 짜라."**

직전 사고: 한 팩트 테이블에만 `market` 컬럼이 빠져 시장 필터가 불가능했다. 그때 "전종목 합산이라 시장구분이 없다"고 잘못 단언했는데, 실제로는 `market`이 종목 차원에 있어야 했다. 설계 실수와 미확인 단언이 겹친 사례다.

- **`dev/DATA_MODEL.md` 먼저 읽는다.** 같은 데이터가 이미 어느 차원에 있는지 확인하고 중복 컬럼을 신설하지 않는다.
- **차원과 팩트를 구분한다.** 불변 속성은 차원 테이블 한 곳, 일별 측정값만 팩트. 팩트마다 차원 컬럼을 denormalize하지 말고 JOIN한다.
- **"나라나 자산군이 하나 더 들어오면?"**을 자문한다. 차원 row 추가만으로 끝나야 정상이다. 팩트마다 컬럼을 추가하는 설계면 틀린 것이다.
- DB 컬럼명도 `dev/NAMING.md`를 따른다. dict 키나 API 필드와 같은 규칙이다.

## §10 — 체계적 디버깅 없이 랜덤 수정

> 강제: 산문 전용 — 디버깅 절차는 검출 불가

**근본 원인 파악 전 수정 시도 금지.** 순서는 넷이다.

1. **근본 원인 조사** — 에러 메시지 완독 → 재현 → 최근 변경 확인 → 데이터 흐름 추적
2. **패턴 분석** — 동작하는 유사 코드를 찾아 차이점을 식별
3. **가설 테스트** — 단일 가설을 최소 변경으로 검증. 실패하면 새 가설. **여러 수정 동시 금지**
4. **구현** — 실패 재현 테스트 작성 → 단일 수정 → 검증

**3회 수정 실패 시 STOP.** 아키텍처 문제를 의심하고 증거와 함께 사용자에게 보고한다.

여러 수정을 동시에 던지면 무엇이 고쳤는지 모르게 된다. 고쳐진 것처럼 보이는 상태가 사실은 다른 걸 깨뜨린 상태일 수 있다.

## §11 — 검증 없이 완료 주장

> 강제: 산문 전용 — 검증 실행 여부는 검출 불가. 훅이 종료를 막을 뿐이다

완료 선언 전 필수 순서는 셋이다. 검증 명령 실행 → 출력 전체 확인 → 출력이 주장을 확인할 때만 선언.

**금지 표현**: "통과할 것이다" / "이제 동작할 것이다" / "수정 완료" / "문제 없어 보인다"

| 주장 | 필요한 증거 | 불충분 |
|------|-----------|--------|
| 테스트 통과 | 테스트 명령 출력에 0 failures | 이전 실행, "될 것" |
| 빌드 성공 | 빌드 명령 exit 0 | 린터 통과 |
| 버그 수정 | 재현 테스트 PASS | "코드 변경함" |

UI 작업은 렌더된 화면을 직접 확인하는 것까지가 검증이다.

## §12 — 공유 체크아웃에서 구현·커밋

> 강제: 산문 전용 — 보드 잔존 훅(⑫)은 머지 후 남은 행을 경고할 뿐이고 브랜치 확인 자체는 검출 불가

> 출처: 원본 프로젝트 실증 (2026-07-20)

다른 세션이 공유 트리를 feature 브랜치로 전환해둔 상태에서 **커밋 직전까지 갔다.** 내 커밋이 남의 브랜치에 섞일 뻔했다.

구현과 커밋과 브랜치 조작은 자기 worktree에서만 한다. 공유 체크아웃은 읽기 구역이다.
**첫 편집 전에 현재 브랜치와 경로를 확인하고**, 공유 경로인데 기본 브랜치가 아니면 멈춘다. 정본 절차는 `workboard/README.md`다.

## §13 — 게이트를 "실물 생기면 켠다"로 미뤄 래칫이 역전됨

> 강제: 검사 28 — 지도와 실물의 양방향 대조. 게이트 등재 자체는 골든 정답지(`tests/run_golden.py`)에 섹션이 찍히는 것으로 확인한다(§22)
> 출처: 하네스 개발 레포 실증 (2026-08-09)

게이트 20~26을 "해당 레이어의 실물이 생긴 뒤 켠다"며 OFF로 뒀다. 전부 대상이 없으면 자연 통과하는 설계였고, 실제로 켜보니 전 항목 통과였다. 끌 이유가 처음부터 없었다.

늦게 켜면 그 시점의 위반부터 baseline 면제 목록에 쌓인다. **켤 수 있을 때 켜지 않는 것이 곧 래칫 위배다.** `kernel/gates/tests_pairing.py` 헤더가 그 논리를 이미 적어두고도 정작 자신은 OFF였다.

**대상이 없어 자연 통과하는 게이트는 지금 켠다. 코드가 쌓인 뒤가 아니라.**

## §14 — 파생하지 않은 설정 리터럴이 게이트를 무음 사망시킴

> 강제: 산문 전용 — 현재 프로파일은 경로를 `CHECK_PATHS` 한 곳에 선언해 파생할 짝 설정이 없다. 짝 설정이 다시 생기면 파생 대조를 게이트로 올린다
> 출처: 하네스 개발 레포 실증 (2026-08-09)

당시 프로파일의 `READS_PREFIX`가 `DB_PREFIX`에서 파생되지 않고 리터럴이었다(둘 다 지금은 없는 이름이다). `DB_PREFIX`를 바꾸면 해당 게이트가 대상 0건을 반환한다. 에러가 아니라 **초록불**이다.

더 나쁜 건 그다음이다. 이 버그를 원인으로 오해해 "레이어 이름은 규약이라 바꿀 수 없다"는 규칙을 만들었다. **버그의 증상을 설계 원칙으로 굳힌 것이다.** 파생으로 고치자 그 규칙 자체가 불필요해졌다.

**설정값이 다른 설정값을 함의하면 파생시킨다. 리터럴 복제는 조용히 깨지고, 그 침묵이 잘못된 원칙을 낳는다.**

## §15 — 꺼진 게이트와 배선 빠진 게이트가 화면상 같음

> 강제: 산문 전용 — 등재 대조를 러너 자신이 하면 자기검사 재귀다(§22). 새 게이트는 픽스처에 위반을 심고 골든 정답지에 섹션이 보이는 것으로 배선을 확인한다
> 출처: 하네스 개발 레포 실증 (2026-08-09)

게이트가 OFF인 것, 배선을 빠뜨린 것, 대상이 없어 통과한 것이 전부 동일하게 보인다. 셋 다 위반 0건이다. 그래서 게이트를 추가하고 배선을 잊어도 아무도 모르고, 검사기가 죽어 있어도 초록불이다.

**"통과"와 "검사하지 않음"을 구분할 수 없는 출력은 검사가 아니다.** 그래서 신규 게이트는 통과 확인만으로 부족하고, 합성 입력으로 실제 발화까지 확인해야 배선된 것으로 본다.

## §16 — 진화 루프를 문서화하지 않아 세션이 루프를 건너뜀

> 강제: 산문 전용 — 지적 발생 자체를 기계가 검출할 수 없다. 검사 30은 절의 강제 표시 누락만 잡는다
> 출처: 하네스 개발 레포 실증 (2026-08-09)

이 하네스의 핵심은 사고를 여기 남기고 검사 가능한 것을 게이트로 올리는 순환이다. 그런데 쓰기(`CLAUDE.md` MD 시냅스)와 읽기(라우팅표)와 승격(일관성 게이트)이 서로 다른 절에 흩어져 있고, **셋을 잇는 문장이 한 줄도 없었다.**

결과: 한 세션에서 하네스 결함 4건을 찾아 전부 게이트로 만들고도 이 파일에는 한 줄도 안 남겼다. 경위는 커밋 메시지로만 갔고, 커밋 메시지는 라우팅표에 없어 다음 세션이 읽지 않는다. §13~§15가 그때 유실될 뻔한 것들이다.

사용자: **"그 레슨을 통해 하네스가 진화한다는 걸 왜 안 적어놓은 거야."**

**시스템의 핵심 동작은 어느 파일에도 안 적혀 있으면 없는 것과 같다.** 파일별 "담는 것"만 적는 서식은 파일 사이에 무엇이 흐르는지를 적게 만들지 않는다. 흐름은 따로 적어야 한다.

## §17 — 관찰 장치 없이 시작해 초기 신호를 잃음

> 강제: 관찰 기록 (`kernel/trace.py`) + 편집 표면 래칫 (`harness_gates/edit_surface.py`)
> 출처: 이 프로젝트 (2026-08-10)

§16 이 잇지 못한 것이 하나 더 있었다. 승격 순환의 **입력**이다.

사고를 `dev/LESSONS.md` 에 남기고 게이트로 올리는 경로는 **사람이 사고를 알아채야** 시작된다. 알아채지 못한 마찰은 그대로 사라진다. 게이트가 걸린 횟수도, 어느 파일에서 반복됐는지도, 어떤 판정이 오탐이었는지도 세션이 끝나면 남지 않는다.

그리고 그 신호가 제일 센 구간이 **하필 프로젝트 초반**이다. 게이트가 제일 많이 걸리고, 관례가 그때 정해지고, 오탐도 그때 드러난다. 코드가 쌓인 뒤에 기록 장치를 붙이면 이미 그 데이터는 없다.

사용자: **"루프를 지금 짜야 하는 이유가 오히려 코드가 없기 때문이다."**

- 훅이 막을 때마다 관찰을 남긴다. 기록 실패가 차단을 막지는 않는다 — 관찰은 차단보다 항상 덜 중요하다.
- 채굴까지가 기계다. **판정은 사람이 한다.** 이 하네스엔 "더 좋아졌다"를 재는 적합도 함수가 없고, 골든 대조는 회귀만 잡지 개선을 못 잰다.
- 적합도 없이 제안과 수용을 자동화하면 루프는 가장 싼 통과 경로로 수렴한다. **면제 목록 늘리기다.** 그래서 편집 표면 래칫이 같은 커밋에 들어갔다. 판정이 수동인 동안에도 그 문을 닫아둬야 나중에 자동화할 여지가 생긴다.
- 거절된 제안은 `dev/REJECTED.md` 에 남긴다. 부정 결과가 사라지면 다음 회고가 같은 제안을 다시 하고, 그 반복이 결국 하나를 통과시킨다.

## §18 — 평가기가 clone 직후부터 반쪽인데 아무도 몰랐음

> 강제: 평가기 자가복구 (`tests/run_golden.py` 가 픽스처 프로파일이 없으면 정본에서 다시 짓는다)
> 출처: 이 프로젝트 (2026-08-10)

폐쇄 루프의 검증 단계로 골든 대조를 재사용하려고 상태를 확인했더니 실패하고 있었다.

원인은 게이트가 아니었다. 픽스처의 `.gitignore` 가 `harness_profile.py` 를 빼고, 그 `.gitignore` 는 바깥 레포에도 적용된다. 즉 픽스처 프로파일은 **한 번도 커밋된 적이 없었다.** clone 하면 파일이 없고, 전 게이트 대조가 프로파일 없는 상태로 돌아 `--bare` 와 똑같은 출력을 낸다.

증상이 고약하다. 실패는 하는데, 화면에 뜨는 것은 "게이트 27건이 통째로 사라졌다"는 diff 다. 그걸 보는 사람은 원인을 게이트에서 찾는다. **평가기가 자기가 반쪽이라고 말하지 않고, 검사 대상이 망가진 것처럼 말한다.**

§15 의 확장이다. 거긴 게이트가 "통과"와 "검사하지 않음"을 구분 못 하는 문제였고, 여기는 평가기가 같은 병에 걸린 경우다. **검사기를 검사하는 것도 검사기이므로, 그쪽이 조용히 죽는 경로도 똑같이 막아야 한다.**

- 평가기가 자기 전제를 못 갖추면 조용히 등급을 낮추지 말고, 다시 갖추거나 그 사실을 말해야 한다.
- 재생성의 정본이 있으면 재생성이 답이다. `tests/fixture_files.py` 가 있는데 파일 하나가 없어서 평가기가 반쪽이 될 이유가 없다.

## §19 — 고칠 수단이 없는 조건으로 차단하면 검사가 아니라 데드락이다

> 강제: 검사 없음 — 산문 전용 · 훅 단계 정책(`dev/HARNESS.md` 「단계」)이 강제분이다. 어느 판정이 추론인지는 사람이 정한다
> 출처: 원류 프로젝트 (2026-08-21)

하네스 개선을 커밋하고 push 승인을 기다렸다. 보드 잠금 훅이 자기 행을 보고 종료를 막았는데, 그 행은 지울 수 없었다 — **머지 전에 지우는 것이 곧 거짓 완료 보고다.** 훅이 막고 모델이 "대기 중"을 찍고 또 막고를 아홉 번 반복하자 연속차단 상한이 훅을 무시하고 턴을 끝냈다. 하네스가 자기 하네스에 걸려 아홉 턴을 태웠다.

먼저 나온 답은 재차단 우회 플래그였다. 사용자가 되물었다 — **"stop hook 이 돈다는 건 니가 뭔가 잘못하니까 도는 건데 이걸 무시하는 루프가 있는 게 맞아? 훅이 너무 이상한 걸 점검해서 에러가 나는 거면 훅을 고쳐야지."** 맞는 말이었다. 훅은 조건이 참이라서 돈 것이고, 참인 조건을 놔둔 채 두 번째부터 입만 막는 것은 진단이 아니라 은폐다.

조건을 열어보니 실제로 틀려 있었다. 훅은 자기 행이 **있기만 하면** 막았는데 그건 *진행 중인 행*과 *머지 후 안 지운 행*을 구분하지 않는다. 앞의 것은 남아 있는 게 정상이다 — 이 하네스는 `wip_` 접두와 파일 핸드오프로 **여러 세션에 걸치는 작업을 전제**한다. 훅이 하네스 자신의 설계와 충돌하고 있었다.

같은 날 짝이 되는 오판이 하나 더 났다. worktree 잔해 훅이 `branch.<브랜치>.remote` 존재를 push 이력으로 읽었는데, `git worktree add -b X origin/<기본>` 이 시작점을 upstream 으로 자동 등록한다. 그래서 **갓 판 worktree 가 만들어진 그 순간부터 "머지 완료, 지워라"** 로 잡혔고, 그 말을 따르면 작업 중인 판을 지운다.

- **차단은 "고쳐라"는 신호다.** 고칠 수단이 없는 조건에 걸면 신호가 아니라 벽이다. 훅을 새로 쓸 때 물을 것은 "이게 참이면 나쁜가"가 아니라 **"이게 참일 때 모델이 할 수 있는 일이 있는가"** 다.
- **우회 플래그는 조건 오류의 답이 아니다.** 조건이 옳은데 대상이 이미 지나간 경우에만 쓴다. 조건이 넓어서 나는 오탐에 쓰면 다음 사람은 왜 막혔는지도 왜 안 막히는지도 못 읽는다.
- **판정 근거가 추론이면 차단 권한을 주지 않는다.** git 상태로 "끝났을 것"을 추측하는 훅은 경고까지다. 검출을 끄면 잔해가 안 보이므로 **끄는 대신 단계를 낮춘다.**
- **원칙을 적는 것과 그 원칙이 모든 분기에 닿는 것은 다른 일이다.** 「실패 시 방향」에 "보드 오탐은 종료 데드락이다 → 통과"가 이미 있었는데, 같은 논리가 "같은 훅이 반복 차단하는 경우"에는 적용돼 있지 않았다.

## §20 — 산문으로 적어둔 규칙은 적어뒀다는 이유로 지켜지지 않는다

> 강제: 검사 없음 — 훅 ⑧-4(`check_workflow_script.py`)가 `agent()` model 미지정을 차단한다
> 출처: 원류 프로젝트 (2026-08-21)

15트랙 리팩토링 감사를 Workflow 툴로 띄웠다. 워커 51개가 떴고 **14개가 결과 없이 죽었다.** 토큰은 cache_read 248M 이 나갔고 그 95%가 비싼 쪽 단가였다.

사고는 독립 사건 셋이 아니라 한 줄 사슬이다. 턴이 먼저 끝나자 정리가 **변경 없는 worktree 를 자동 제거**했고, 그 안에서 읽던 워커 둘이 사라진 트리를 52분간 재생성·재읽기만 하다 끝났다. 앞 트랙 하나를 고쳐 resume 했더니 저널이 **위치 기반 prefix 캐시**라 뒤 23개가 전부 다시 돌았다. 그 재실행 호출에 model 이 없어 워커가 메인 모델을 상속했고, 그 모델 전용 거부 정책에 11개가 걸렸다. 거부는 결과 행을 안 남겨 파이프라인이 **영원히 기다렸다.**

핵심은 마지막 고리가 **이미 알려져 있었다**는 것이다. `CLAUDE.md` 모델 라우팅에 「워크플로우 스크립트의 에이전트는 model 미지정 시 메인 모델을 상속한다」가 그대로 적혀 있었다. 적어뒀는데 안 지켜졌고, 문구까지 좁아서(「팬아웃 스테이지는」) 사고가 난 구현·검수 스테이지는 아예 가리키지도 않았다.

- **적어뒀다는 것과 지켜진다는 것은 다른 사실이다.** 일관성 게이트 ①("검사 가능한 규칙은 게이트로")이 겨냥하는 실패가 이것이다. 이 사고의 조치는 규약 신설이 아니라 **기존 산문의 기계 승격**이었다.
- **툴 문서의 "기본값"은 그 문서가 가정한 메인 모델에서만 기본값이다.** 메인이 바뀌면 상속되는 것 전부(모델·단가·거부 정책)를 다시 본다.
- **백그라운드 워커가 도는 동안 "메인 턴 종료"는 무해한 이벤트가 아니다.** 턴 종료에 걸린 정리가 워커 발밑을 지운다. 정리 대상이 될 수 없는 상태를 먼저 만들거나, 워커가 도는 동안 턴을 끝내지 않는다.
- **캐시는 내용이 아니라 위치로 깨질 수 있다.** "안 고친 건 캐시되겠지"는 prefix 캐시에서 틀린다. 일부만 다시 돌리는 것은 resume 이 아니라 개별 스폰이다.
- **규약 밖 경로는 규약이 0개 적용된 경로다.** 새 툴을 쓰기 전에 하네스 지도에 있는지 본다. 없으면 쓰기 전에 한 줄이라도 등재한다 — 쓰고 나서 사고 기록으로 등재하는 쪽이 항상 더 비싸다.

## §21 — 훅도 구현만 있고 실행이 안 되면 무음으로 죽는다

> 강제: `tests/test_hooks.py` — 훅 판정 함수를 직접 실행하는 행동 테스트. import 누락·NameError 는 여기서 잡힌다
> 출처: 실운영 스냅샷 대조 (2026-09-07)

`check_worktree_residue.py` 의 `_alive()` 가 `subprocess.run` 을 쓰는데 `import subprocess` 가 없었다. 호출마다 NameError 가 났지만 방어용 `except Exception: return True` 가 그걸 삼켰고, 결과는 "lock 걸린 worktree 는 PID 생사와 무관하게 항상 살아있음" — 크래시 잔해 검출이라는 이 훅의 핵심 케이스가 **무음으로 꺼진 채** 커밋돼 있었다. 실운영본과의 diff 대조가 아니었으면 발견 경로가 없었다.

방어적 except 는 판정 오류만 삼켜야 하는데 **코드 결함까지 삼킨다.** "판정 불능이면 안전한 쪽" 설계가 옳더라도, 그 안전망 아래에서 함수가 한 번도 성공한 적이 없는지는 별도 신호가 필요하다 — 그 신호가 행동 테스트다.

- **훅의 판정 함수는 최소 1회 실제로 실행하는 테스트를 남긴다.** import 누락·오타는 코드 리뷰가 아니라 실행이 잡는다.
- **`except Exception` 으로 안전값을 돌려주는 함수가 제1 후보다.** 실패가 정상 경로처럼 보이는 곳부터 테스트한다.

## §22 — 구현과 등재는 다른 사실이다: 러너에 없는 게이트는 존재하지 않는다

> 강제: 산문 전용 — 등재 대조를 러너 자신이 하면 자기검사 재귀다. 새 게이트는 골든 정답지에 그 섹션이 찍히는 것으로 등재를 확인한다(`tests/run_golden.py`)
> 출처: 실운영 스냅샷 대조 (2026-09-07)

`kernel/gates/core.py` 에 `check_header_path_comment` 가 온전히 구현돼 있었지만 `kernel/runner.py` 의 섹션 목록에 없었다. 호출되지 않으니 [FAIL] 도 [SKIP] 도 안 찍혔다 — 러너의 "무음 통과 없음" 계약은 **등재된 게이트**에만 성립하고, 등재 누락 자체는 그 계약 밖이었다. 범용화 리팩터에서 함수는 옮기고 등재를 빠뜨린 것으로 추정되며, 실운영 레지스트리와의 전수 대조 전까지 아무도 몰랐다.

- **새 게이트의 완료 조건은 "함수가 있다"가 아니라 "골든 정답지에 그 섹션이 보인다"다.** 픽스처에 위반 1건을 심고 정답지에 등장을 확인해야 등재까지 검증된다.
- **리팩터에서 옮긴 함수는 소비처(등재부)를 grep 으로 확인한다.** import 성공은 등재가 아니다 — 게이트 함수는 아무도 import 하지 않아도 조용하다.

## §23 — 게이트는 판정만 한다: 러너가 파일을 쓰면 세션 종료가 커밋을 더럽힌다

> 강제: `tests/test_harness_self.py` `test_runner_leaves_tree_clean` — 전 게이트를 돌린 뒤 `git status` 가 그대로인지 본다
> 출처: 그림 엔진 재조립 (2026-09-09)

검사 48 의 엔진 위임이 `kernel.diagram.validate` 를 불렀고, 그 함수가 편의로 정본의 `revision` 을 HEAD 로 되썼다. 작성 루프에서는 편했다. 그런데 같은 함수를 Stop 훅의 전량 검사가 부르니 **세션이 끝날 때마다 커밋된 그림 정본 3개가 바뀌고 영수증 해시가 어긋났다.** 커밋 직후 트리가 깨끗해야 할 순간에 게이트가 트리를 더럽힌 것이다. 알아챈 건 편집기 파일 변경 알림이었지 게이트가 아니었다.

- **판정 함수와 되쓰기 함수를 한 이름에 두지 않는다.** `validate` 는 읽기만, `deliver` 만 쓴다. 게이트가 부르는 경로에는 쓰기가 없어야 한다.
- **러너를 돌린 뒤 트리가 깨끗한가는 골든이 못 본다.** 골든은 출력만 대조한다. 그래서 자체 테스트에 `git status` 전후 대조를 뒀다.

## §24 — 완료 표식을 먼저 지우면 청소 도중 죽은 잔해가 주인을 잃는다

> 강제: 산문 전용 · 두 Stop 훅(`check_editing_lock.py`·`check_worktree_residue.py`) 안내문이 순서를 유도한다. 위반은 "행을 지운 순간 worktree 가 있었다"는 지나간 상태라 Stop 시점에는 관측할 수 없다
> 출처: 원류 프로젝트 (2026-09-15)

완료 순서가 merge → 보드 행 제거 → `git worktree remove` → `git branch -d` 였다. 행부터 지운 세션이 worktree 청소 도중 죽었고, worktree 만 남았다. 보드에 기록이 없으니 다른 세션은 그것이 진행 중인지 버려진 것인지 가릴 수 없었다.

원류는 산문 순서만 바꿨다. 그런데 보드 잠금 훅은 머지된 행을 보면 여전히 "보드에서 제거하세요" 만 말했다 — **산문을 고쳐도 훅 안내문이 옛 순서를 계속 유도했다.**

- **"끝났다"는 표식은 정리의 마지막 단계로 둔다.** 표식이 남아 있는 한 미완료로 읽혀야 중간에 죽어도 추적된다.
- **순서 규칙을 바꾸면 그 순서를 말하는 훅 안내문도 grep 한다.** 모델은 산문보다 매 턴 보는 훅 출력을 따른다.

## §25 — 백그라운드 작업 중 Stop 반복 차단: 작업 공간과 본체를 안 가르면 게이트가 작업을 막는다

> 강제: 훅 ⑧-6·⑧-7(`check_pretool.py`, 판정 `kernel/isolation.py`) — 메인 체크아웃 편집과 보드 미등록 편집을 막고 push·PR·merge 직전에 `--verify` exit 0 을 요구한다. worktree 안 ⑨·⑬ 은 `[WIP]` 알림으로 낮췄다(`kernel/hook.py`)
> 출처: 이 레포 (2026-09-28, 세션 cde18a4e)

스택 중립 P1 을 executor 에 위임하고 메인 세션은 기다렸다. 워커가 커널을 고치는 동안 메인 세션의 턴이 끝날 때마다 Stop ⑬ 이 돌았고, 그림 검사 48 이 "노드가 가리키는 행이 없다 · 영수증 해시가 다르다" 로 네 번 막았다(`harness_trace.jsonl` 09:29 · 09:30 · 09:32 · 10:40). 막힌 조건은 전부 워커가 쓰는 중인 파일이었고 그림 deliver 는 커밋 뒤에만 가능하다 — 메인 세션이 그 자리에서 할 수 있는 일이 없었다. §19 의 "고칠 수단 없는 차단" 이 형태만 바꿔 다시 났다.

원인은 게이트가 아니라 자리다. "단일 세션이면 메인 체크아웃에서 작업해도 된다" 가 정본이라 모든 세션이 메인에서 작업했고, 작업 중인 트리와 합쳐지는 본체가 같은 트리였다. 게이트는 본체를 지키려고 있는데 작업 중인 트리를 매 턴 지키려 들었다.

사용자 지시: "claude 도 codex 도 worktrees 랑 workboard 쓰는 거 강제해야 한다 … 무조건" · "일하는 공간은 검사 예외" · "똥 싸는 중은 노터치, 나온 걸 손 잘 씻었나 검사".

- **작업 공간과 본체는 다른 트리여야 한다.** 격리가 선택이면 아무도 안 하고, 그러면 게이트가 작업을 막는다. 세션이 하나여도 같다.
- **검사 시점은 합칠 때다.** 작업 중 판정은 알림까지고, push·PR·merge 직전에 그 체크아웃에서 전량 검사를 돌린다. 판정을 끄는 게 아니라 차단 시점을 옮긴 것이다.
- **워커가 도는 동안 메인 턴 종료는 무해하지 않다** — §20 과 같은 고리다. worktree 안에서는 Stop 이 막지 않으므로 기다리는 턴이 안전해졌다.

## 일관성 게이트 — 근본 원인 진단

> 규칙 정본: `CLAUDE.md` 일관성 게이트
> 출처: 원본 프로젝트 사용자 진단 (2026-06-26)

왜 매번 대규모 리팩토링이 터지는가. 원인은 둘이다.

1. **세션마다 새 개발자다.** 매번 컨텍스트 없는 새 Claude가 기능을 붙인다. 각자 제 스타일로 짜니 서비스가 일관되게 확장되지 않고 스파게티가 된다.
2. **MD 규칙은 산문일 뿐 강제가 아니다.** "400줄 지켜라"는 글은 세션이 길어지고 컨텍스트가 압축되면 흘러내린다. **검사 가능한 규칙을 산문으로 단속하려는 것 자체가 실패 메커니즘이다.** MD를 더 써도 안 고쳐진다.

이 진단이 "규칙을 MD에 추가"에서 "**규칙을 `kernel/gates/`에 추가**"로 방향을 바꾼 근거다. MD는 왜만 적고 강제는 게이트가 한다.

### 래칫 원칙의 실증 근거

> 출처: 원본 프로젝트 전수감사 (2026-07-16)

대규모 정리는 반드시 **그 상태를 잠그는 검사와 같은 커밋**으로 끝낸다. 게이트 없는 정리는 재발한다.
545파일 전수감사 실증: **게이트가 있던 규칙은 위반 0, 산문뿐이던 규칙만 재누적됐다.**
