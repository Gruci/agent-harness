# dev/TESTING.md — 행동과 경계 테스트

> 담는 것: 책임에 따른 테스트 선택과 회귀 검증 기준. 담지 않는 것: 실행 절차(→ [workflows/test.md](workflows/test.md)). 읽는 시점: 테스트를 작성하거나 변경 계약을 검증할 때.

## 실패를 먼저 확인한다

버그 수정은 재현 테스트를 먼저 실행하여 실패를 확인한다.
새 행동은 인수 조건을 검증하는 테스트를 작성한 뒤 최소 구현으로 통과시킨다.
오탈자나 설정값 하나의 수정에 구현을 그대로 복제하는 테스트를 추가하지 않는다.
단순 리팩터링은 기존 행동 테스트로 변경 전후의 계약을 확인한다.

## 책임에 따른 선택

| 대상 | 검증할 계약 | 실행 방법 |
|---|---|---|
| 정책 | 계산과 상태 전이 및 불변 조건 | 네트워크 없는 단위 테스트 |
| 유스케이스 | 업무 절차와 실패 처리 | 선언된 포트를 대역으로 제공한다 |
| 어댑터 | 실제 저장소나 서비스와의 호환 | 테스트 저장소 또는 외부 경계 픽스처 |
| 전달 | 입력과 출력 및 오류 처리 | 선택한 프레임워크의 실제 요청 경로 |
| 공개 포트 | 호출 서명과 결과 및 실패 계약 | 계약에 맞는 대역을 실행한다 |

정책의 내부 함수를 가짜로 바꾸고 정책이 검증됐다고 보고하지 않는다.
외부 I/O와 시각처럼 테스트가 제어해야 할 경계만 대체한다.
통합 테스트는 내부 호출을 모킹하는 대신 실제 테스트 자원을 사용한다.

## 포트 대역

포트를 선언하지 않은 경계에 대역을 의무화하지 않는다.
선언한 포트는 공개 계약을 구현하는 대역으로 유스케이스를 실행해 검증한다.
이름이 Fake로 시작하는 클래스의 존재만으로 통과시키지 않는다.
기계 검사로 확인한 범위와 실제 행동 테스트가 확인한 범위를 구분한다.
지원하지 않는 언어의 계약 검사는 미검증으로 보고한다.

## 언어와 도구

테스트 명령은 프로젝트에서 선택한 언어와 도구에 맞춰 구성한다.
하네스가 Python으로 실행된다는 이유로 제품 테스트에 pytest를 강제하지 않는다.
소스 위치는 [분류 정본](COMPONENTS.md)에 연결한다.
업무 규칙의 기대값과 실패 조건을 테스트에 적으며 함수 이름 접두어로 책임을 판단하지 않는다.

## 완료 근거

실행 명령과 종료 코드를 기록한다.
테스트가 선택되지 않은 실행은 성공 근거가 아니다.
필수 도구가 없거나 구문 분석을 못 하면 미검증이며 완료가 아니다.
실제 외부 서비스 연결을 대체했다면 검증한 범위를 명시한다.

## 하네스가 돌리는 제품 테스트

프로파일 `TESTS` 에 선언한 명령은 하네스가 직접 돌린다(`kernel/tests_run.py`). 선언 서식의 주석은 `profiles/_template.py` 에 있다.

| 항목 | 계약 |
|---|---|
| 건수 근거 | 명령에 JUnit XML 보고서 자리 `{report}` 가 하나 있어야 한다. 실행마다 새 임시 위치에 쓰고, 실행 0건·보고서 없음·깨진 보고서는 실패다. 명령이 0으로 끝나도 보고서에 실패가 있으면 실패다 |
| 후보 고정 | 실행 중 HEAD 가 바뀌거나, 추적 파일이 바뀌거나, 무시되지 않은 새 파일이 생기면 실패다. 테스트 산출물(캐시·커버리지)은 `.gitignore` 에 둔다 |
| 종료 코드 | 0 통과, 1 실패, 2 미검증(도구 없음·시간 초과). finish 는 이 코드를 그대로 낸다 |
| 미선언 | `[SKIP] Product tests` 를 찍고 통과한다. 이 상태의 finish·CI 통과를 "제품 테스트 통과"라고 부르지 않는다. 꼭 돌아야 하면 `REQUIRED_CHECKS` 에 `"tests"` 를 넣는다 |

돌아가는 곳과 보장 범위는 아래와 같다. `--verify`(120초 상한)와 매 턴 Stop 에는 넣지 않는다 — 이 하네스 자체의 테스트 일부만 해도 180초가 걸렸다.

| 경로 | 제품 테스트 |
|---|---|
| `kernel.task finish` (로컬 합치기, PR 흐름의 PR 열기 전, TEAM 제출) | `--verify` 가 통과한 같은 트리에서 돈다 |
| 템플릿 CI(`.github/workflows/harness.yml`) | Gates 다음 단계에서 돈다. 후보 기록은 둘 다 통과해야 남는다 |
| 손으로 하는 push·merge 의 합치기 전 훅(⑧-7) | 돌지 않는다 — `--verify` 만 보장한다 |
화면 변경은 소비 API와 연결을 확인하고 렌더링을 검사한다.

## 병렬 자원과 소비 계약

작업 사본마다 DB 파일이나 스키마와 캐시 위치를 분리한다.
테스트 서버는 운영체제가 빈 포트를 배정하도록 실제 소켓을 연 채 사용한다.
공유 통합 DB의 마이그레이션은 해당 DB의 트랜잭션이나 배포 도구로 직렬화한다.
API와 실제 소비자를 함께 실행하고 응답 계약이 바뀌면 소비 테스트가 실패하는지 확인한다.
원류 examples/harness-reference의 실행 예제는 SQLite와 HTTP 및 두 Git 작업 사본으로 이 경계를 검증한다.
예제의 성공은 지정하지 않은 외부 제품이나 다른 DB의 운영 검증을 대신하지 않는다.
