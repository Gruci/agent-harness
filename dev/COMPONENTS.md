# 컴포넌트 분류와 사용자 결정

> 담는 것: 그래프 정본과 분류 제안 및 사용자 응답을 검사에 연결하는 계약. 담지 않는 것: 조립 순서(→ [조립 절차](workflows/harness-assembly.md))·JSON 필드 정의(→ [서식](../docs/architecture/components.schema.json)). 읽는 시점: 첫 코드와 구조 변경을 계획할 때.

## 분류를 먼저 결정한다

제품 소스는 승인된 컴포넌트와 역할에 정확히 하나씩 속해야 한다.
AI는 새 분류가 필요하면 이름과 책임 및 제외 책임을 먼저 제안한다.
제안에는 공개 계약과 실제 배치 및 허용 의존 관계의 차이를 포함한다.
제안은 plan의 「분류 제안」 행에 실어 plan 승인과 함께 받는다.
plan 밖에서 `[DECISION]`이 나오면 그 변경만 보류하고 사용자에게 알린다.
사용자는 승인하거나 수정하거나 보류한다.
기존 승인 범위의 일반 수정은 다시 질문하지 않는다.
사용하지 않는 역할의 빈 폴더를 만들 필요는 없다.

## 그래프와 지도

[컴포넌트 그래프](../docs/architecture/components.json)가 허용 구조의 정본이다.
소스에서 발견한 의존은 관측 결과이며 자동으로 허용 관계가 되지 않는다.
프로젝트가 선택한 역할 사이의 의존 방향도 그래프에 선언한다.
제품 코드가 아닌 테스트와 생성물 및 하네스 기반 코드는 이유를 붙여 명시한다.
분류되지 않은 파일과 소유 컴포넌트가 둘 이상인 파일은 성공으로 처리하지 않는다.
planned 노드는 코드 없이도 존재할 수 있다.
implemented 노드는 실제 소스 근거가 필요하다.
retired 노드에 코드가 남으면 실패한다.

`python -X utf8 -m kernel.feature_map`은 현재 그래프와 소스로 기능 지도를 생성한다.
`python -X utf8 -m kernel.feature_map --check`는 파일을 수정하지 않고 차이만 검사한다.
저장 훅은 승인된 그래프의 기능 지도를 갱신한 뒤 검사를 수행한다.
지도는 현재 파일의 해시를 근거로 사용하며 존재하지 않는 커밋이나 소스 위치를 만들어내지 않는다.
기존 다이어그램 엔진으로 작성한 그림은 별도로 소스 증거와 렌더 결과를 검증한다.
기능 지도와 엔진 그림을 모두 만들도록 강제하지 않는다.

## AI가 사용자에게 알린다

훅은 구조 결정이 필요하면 `[DECISION]`과 `needs_decision` 자료를 반환한다.
이를 받은 AI는 분류안을 사용자에게 보여주고 답을 요청해야 한다.
알림 수단은 해당 AI가 제공하는 질문 도구나 대화 메시지를 사용한다.
Orca와 특정 호스트 API는 필요하지 않다.
같은 문제에는 같은 알림 ID를 유지하고, 한 세션에서 반복 저장할 때는 중복 알림을 줄인다.
다음 세션은 결정 대기 상태를 읽어 이어받는다.
훅 출력만으로 사용자가 알림을 봤다고 주장하지 않는다.

## 결정 기록과 적용

`kernel.graph_workflow propose`는 기준 그래프와 후보 그래프를 묶은 제안을 저장한다.
`pending`은 결정 대기 중인 제안을 읽기만 하고 파일을 수정하지 않는다.
AI는 사용자 응답을 받은 뒤 `decide`에 선택과 실제 응답 및 대화 참조를 기록한다.
`apply`는 승인한 내용과 기준 그래프가 일치할 때만 정본에 반영한다.
응답이 없는 상태를 승인으로 간주하지 않는다.
approved 표시만 직접 추가해도 응답 기록과 제안이 일치하지 않으면 통과하지 않는다.
승인 후 내용이 바뀌면 새 제안으로 검토한다.
동시 작업으로 기준 그래프가 달라지면 기존 승인으로 덮어쓰지 않는다.
거절하거나 보류한 제안을 반복 저장으로 새 요청처럼 만들지 않는다.

이 검사는 로컬 기록의 일관성을 검증한다.
사용자가 실제로 말했는지 암호학적으로 인증하는 장치는 아니다.
AI가 사용자의 말을 지어내지 않는 것은 작업 절차의 책임이다.
사용자 대화를 위조할 수 없는 별도 호스트 서비스를 전제로 하지 않는다.

## 저장과 완료는 다르다

저장 후 훅은 이미 쓴 파일을 되돌리지 않는다.
분류가 아직 결정되지 않은 코드는 완료 검증을 통과할 수 없다.
해당 변경을 보류하고 독립적인 승인 범위의 작업은 계속할 수 있다.
사용자 응답을 기다리는 일만 남았으면 Stop 훅은 정상 종료해 사용자가 답할 수 있게 한다.
`python -X utf8 -m kernel.runner --verify`의 성공만 완료 근거로 사용한다.
필수 도구나 분석기를 실행하지 못하면 `[TOOL]`이며 완료 성공이 아니다.
검사 게이트는 정본과 결정 기록을 변경하지 않는다.
제안 기록과 지도 생성은 훅 처리기나 명시적 명령이 수행한다.

## 언어와 포트

초기 서식은 개발 언어를 정하지 않는다.
선택한 스택의 소스 패턴과 분석 및 검사 명령은 첫 코드 전에 연결한다.
기본 구문 분석 예시는 Python 한 가지다.
다른 언어의 분류도 가능하지만 분석기가 없으면 의존 검사는 미검증으로 남는다.
지원하지 않는 언어를 Python으로 바꾸거나 검사 성공으로 표시하지 않는다.
선언한 Protocol만 포트 등록과 페이크 계약 검사를 요구한다.
페이크 이름의 존재만으로 성공하지 않는다.
완료 검증은 등록된 계약 테스트를 실행해 테스트 수, 성공 여부, 페이크 메서드 호출을 확인한다.
정적 호출 분석으로 알 수 없는 동적 경로는 미검증으로 남긴다.
