# workboard/ — 과업 보드와 worktree 프로토콜

> 담는 것: 지금 누가 어떤 과업을 맡고 있는지(이 디렉토리의 파일들)와 과업 시작부터 완료까지의 절차. 담지 않는 것: 남은 일(→ `docs/BACKLOG.md`)·세션 행동 규칙(→ `CLAUDE.md`)·훅의 차단·경고 구분(→ `dev/HARNESS.md`). 읽는 시점: 과업을 시작하기 전.

## 자리가 레포 루트인 이유 — 에이전트 중립

보드와 worktree 는 **어느 에이전트의 것도 아니다.** `.claude/` 밑에 두면 Codex 가 Claude 전용
폴더를 드나들어야 하고, 에이전트마다 자기 폴더에 두면 보드가 갈라진다. 같은 기능을 다루는
에이전트는 같은 보드를 봐야 한다. 과업을 에이전트별로 나누지 않으며, 담당 도구를 밝힐 일이 있으면 과업 파일 안에
`- 담당: claude` 처럼 적는 것으로 충분하다. 과업이 겹치는지 판정하는 코드도 하나뿐이다. `kernel/workboard.py` 를
Claude 훅과 Codex 진입점(`kernel/hook.py`)이 같이 쓴다.

## 보드는 공유 체크아웃 한 곳이다

**과업 파일은 공유 체크아웃(메인 체크아웃 루트)의 `workboard/` 에만 둔다.** 이 README 가 git 으로
추적되므로 worktree 안에도 같은 경로가 생기지만, 거기에 쓴 과업 파일은 다른 세션이 보지 못한다. 보드가
세션 수만큼 갈라져 공유 채널이 성립하지 않는다.

훅은 `git rev-parse --git-common-dir` 로 공유 루트를 찾아 항상 한 곳을 본다
(`kernel.workboard.board_dir()`). 사람이 볼 때도 공유 체크아웃 경로에서 `ls` 한다.

## 이 디렉토리는 git 에 없다

`README.md` 하나만 추적하고 **과업 파일은 `.gitignore`** 로 제외한다. 세션이 전부 같은 머신에서
돌므로 파일시스템이 곧 공유 채널이다. 보드까지 git 을 거치게 하면 두 가지 문제가 생긴다. 모든 세션이 한 파일의
같은 자리를 고쳐 **충돌**하고, 보드를 다른 세션에 보이려면 **머지가 필요**해진다. 이 하네스의 원래 프로젝트인 MIS 에서
2026-09 에 실제로 재 보니 그 비용이 보드 전용 PR 51건(전체 PR 의 25%)과 충돌 해소 34건이었다.

대가는 보드의 이력이 남지 않는다는 점이다. 보드는 "지금" 상태만 담고, 끝난 과업은 git log 와
`docs/tasks/archive/` 에 남으므로 이 손실을 감수한다. 이 방식은 모든 세션이 같은 머신에 있다는 전제에 기댄다. **다른 머신이나
클라우드 세션이 섞이면 이 전제가 깨진다.**

## 파일 하나가 과업 하나

파일명은 **수정 범위**다. 랜덤 식별자를 쓰지 않는다. `ls` 만 해도 겹침이 보여야 하고,
두 세션이 같은 범위를 잡으려 하면 파일명이 같아서 작업을 시작하는 시점에 바로 걸린다.

이름은 `<영역>-<대상>` 두 부분으로 짓는다. 영역은 화면 경로나 API 경로의 첫 세그먼트, 또는 하네스 영역
(`gates`·`hooks`·`docs`·`ci`)이다. 범위의 단위는 **파일 경로가 아니라 화면이나 기능**이다. 한 세션은
컴포넌트만, 다른 세션은 CSS 만 고치더라도 앞쪽이 클래스명을 바꾸면 뒤쪽 작업은 화면에 반영되지
않는다. 경로를 하이픈으로 이어 붙인 이름(`frontend-src-components-…`)은 쓰지 않는다.
**같은 범위에 다른 이름을 붙이면 겹침을 잡지 못한다.** 새 이름을 짓기 전에 `ls` 로 기존 과업을 확인한다.

### 서식

```markdown
- 범위: admin-report-viewers
- 과업: feat/report-viewers-sector-tabs #sid:0e6cda52
- 항목:
  - [x] 부문 탭으로 전환
  - [ ] 제목 폰트 키우기      (2026-09-16 추가 요청)
- 손대는 곳:
  - frontend/src/components/admin/salesStatus/*
  - web/static/admin/admin.css
- 시작: 2026-09-16
- 상태: 진행
```

- `#sid` 는 실행 환경의 session_id 앞 8자다. 식별자가 제공되지 않으면 작업용 ID 를 한 번
  만들어 쓰되, 런타임 ID 로 검증된 값이라고 주장하지 않는다. **훅은 "내 과업인가"를 파일명이
  아니라 이 태그로 판정한다.** 그래서 범위 이름을 바꿔도 자기 과업을 남의 것으로 착각하지 않는다.
- `손대는 곳` 에는 글로브 패턴을 적는다. 편집할 때 `check_workboard_overlap.py` 가 다른 세션의 과업과
  대조한다. 겹쳐도 경고만 하고 막지 않으므로 넓게 적어도 된다.
- `상태` 는 `진행` 으로 시작해 PR 이 나가면 `PR#n` 으로 바꾼다. 과업이 겹치면 이 값으로 순서를 정한다.
- 자기 과업 파일만 고치고, 다른 세션의 파일과 커밋하지 않은 변경은 건드리지 않는다. 위임받은 워커는 부모 세션의 과업
  파일을 같이 쓰고, 배정된 파일만 수정한다.

## 착수 — 같은 범위가 이미 있으면 묶는다

실제로 과업이 늘어나는 경우는 한 화면에 변경이 여러 개 필요할 때다. 과업을 여러 개로 흩지 말고 한 과업으로 묶는다.

| workboard 에 그 범위가 | 하는 일 |
|---|---|
| 없다 | 새 과업 파일을 만들고 시작한다 |
| 있고 `상태: 진행`(PR 전) | 그 파일의 `항목` 에 줄을 추가하고, **그 과업을 잡은 세션이 함께 처리한다** (합류) |
| 있고 `상태: PR#n` | 그 과업의 브랜치를 기준으로 새 worktree 를 만든다 (쌓기) |

기본은 합류다. 쌓기는 앞 과업이 이미 PR 로 나가 더 손댈 수 없을 때만 쓴다. 쌓는 이유는 속도가
아니라 **정확성**이다. 뒤 세션이 앞 과업의 결과 위에서 작업하므로 이름이 서로 어긋날 수가
없다. ⚠️ **쌓은 과업은 머지 순서를 지켜야 한다.** 뒤 과업을 먼저 머지하면 앞 과업의 커밋이 조상으로 딸려 들어간다.

```bash
# 쌓기: 기본 브랜치가 아니라 앞 과업 브랜치에서 딴다
git worktree add worktrees/<범위>--<sid8> -b <브랜치> <앞-브랜치>
```

## 작업 격리

구현은 세션 수와 상관없이 자기 worktree 에서만 한다. 공유 메인 체크아웃에서는 조회, 보드 관리, plan 작성만 한다.
Claude·Codex 양쪽에서 편집 전 격리 가드(⑧-6)와 push·PR·merge 직전 검사(⑧-7)가 이를 강제하고, 판정은 `kernel/isolation.py` 가 한다.

| 어디서 | 판정 | 예외 |
|---|---|---|
| 메인 체크아웃 편집 | 차단 — worktree 생성·진입 명령을 제시한다 | `workboard/**`·`docs/tasks/**`·바뀐 줄 1줄 이하 |
| 어디서든 편집 | 내 `#sid` 과업 파일이 없으면 차단 — 서식을 제시한다 | 같은 예외. 등록 자체는 막지 않는다 |
| worktree 안 저장·턴 종료 | 게이트는 돌지만 막지 않는다. 합칠 때 막힐 목록만 `[WIP]` 머리말을 달아 알린다 | — |
| `git push`·`gh pr create`·`gh pr merge`·`git merge` | 그 체크아웃에서 `--verify` 가 exit 0 이 아니면 차단 — `[TOOL]`·`[DECISION]` 이 나오거나 러너를 실행하지 못해도 통과가 아니다 | 하네스가 없는 체크아웃 |

1줄 예외는 `CLAUDE.md` 4단계 워크플로우의 예외(오탈자·설정값 1줄)를 기계로 판정한 것이다. 줄 수만 보고 파일 종류는 보지 않는다.
세션 식별자가 없거나 git 조회가 실패해 판정할 수 없으면 편집 가드는 경고만 한다. 이때도 막으면 모든 편집이 막혀 복구할 방법이 없다.

- worktree 위치는 **공유 체크아웃 루트 기준 상대경로 `worktrees/<이름>` 하나로 고정**이고,
  **이름은 workboard 범위 이름 + `--<sid8>`** 이다. 절대경로, 외부 디스크, 다른 worktree 안에는
  만드는 것을 허용하지 않는다. 명령은 공유 루트에서 상대경로로 실행한다. 이렇게 하면 `ls workboard/` 와
  `git worktree list` 결과를 눈으로 바로 맞춰 볼 수 있다. `kernel/worktree.py` 가 Claude·Codex 양쪽에서
  worktree 를 만들 때 이름과 위치를 강제한다. 이름이 범위와 맞는지는 내 보드 파일이 있을 때만 검사한다.
- worktree 만들기와 들어가기는 두 단계로 나뉜다. worktree 목록의 정본은 폴더가 아니라 `git worktree list` 다.

  ```bash
  git worktree add worktrees/<범위>--<sid8> -b <브랜치> origin/<기본브랜치>
  # Claude 세션은 이어서 EnterWorktree(path="worktrees/<범위>--<sid8>") 로 진입한다
  ```

  `EnterWorktree(name)` 으로 새로 만드는 방식은 쓰지 않는다. 그 툴은 생성 위치가 `.claude/worktrees/` 로
  고정돼 위의 위치 규약과 어긋난다. 훅이 이를 막고 위 두 명령을 안내한다. `path` 로 기존 worktree 에 들어가는 방식은 위치와
  상관없으므로 그대로 쓴다.
- 생성 기준 브랜치는 원격 기본 브랜치의 실물을 확인해 고른다. 브랜치 이름은 작업 성격에
  맞는 접두(`feat/`·`fix/`·`perf/`·`chore/`·`docs/`)를 쓴다.
- 구현과 검증은 같은 worktree 에서 수행한다.
- 의존성 디렉터리를 다른 worktree 에 junction 이나 symlink 로 연결하지 않는다. 필요한
  의존성은 해당 트리에 설치한다.
- 레포 안에 두는 worktree 디렉터리는 로컬 git 제외 설정에 등록해 검색과 검사 대상에 섞이지 않게 한다.
- 같은 기능을 위임받은 워커는 부모 worktree 를 같이 쓰고, 파일별 편집 담당을 나눠 충돌을 막는다.
  별도 PR 을 만드는 독립 트랙만 별도 worktree 로 격리한다.
- 실행 중인 워커의 worktree 는 제거하지 않는다. worktree 를 자동으로 정리하는 실행 환경에서 독립 트랙을
  쓰면, 작업 전에 git 이 추적하지 않는 표식 파일과 `git worktree lock` 으로 보호한다.
- 각 worktree 에서 검사는 그 체크아웃의 커널을 사용한다.

## 완료

1. 승인된 범위의 구현과 검증을 완료한다.
2. 두 작업 문서를 공통 개발 절차에 따라 `docs/tasks/archive/` 로 보관한다.
3. 커밋과 원격 반영은 사용자 승인 범위와 실행 환경 지침에 맞춰 수행한다. push·PR·merge 직전에
   훅이 그 체크아웃에서 `python -X utf8 -m kernel.runner --verify` 를 돌린다. worktree 안에서
   쌓인 `[WIP]` 목록을 여기서 비워야 통과한다. 원격에 PR·CI 가 있으면 push → PR →
   **CI 통과 확인** → merge 순이다. CI 결과를 확인하는 명령은 다른 명령과 묶지 않고 단독으로 실행한다.
   파이프나 체인을 붙이면 그 명령의 exit code 가 가려져 훅이 막는다.
4. 머지한 자기 worktree 만 제거하고 그다음 자기 브랜치를 정리한다.
5. **자기 과업 파일 삭제는 맨 끝이다.** 머지 직후 같은 턴에 한다. 과업 파일이 남아 있으면 Stop 훅
   `check_worktree_residue.py`·`check_editing_lock.py` 가 턴을 끝낼 때 경고한다.

과업 파일이 있다는 이유만으로 진행 중인 세션이 끝나지 못하게 막지 않는다.
머지 여부를 추정해 파일이 남았다고 판정한 결과는 경고일 뿐이다. 확인 없이 파일을 지우지 않는다.

## 겹친 채로 갈 때

workboard 는 겹침을 알려줄 뿐 해소하지 않는다. 이미 둘 다 편집 중이면:

1. **먼저 PR 을 낸 쪽이 우선이다.** `상태: PR#n` 이 순서를 고정한다.
2. 나중 쪽은 앞이 머지된 뒤 자기 브랜치에 기본 브랜치를 merge 해서 해소한다.
3. **해소 직후 전체 검증을 다시 돌린다.** 충돌 해소도 코드를 바꾸는 일이기 때문이다.
